TriSupport IA

Une application qui classe et priorise automatiquement des demandes de support informatique en JSON, avec un modèle de langage qui tourne en local.

  • Python
  • FastAPI
  • Docker Compose
  • Ollama (Qwen3 8B)
  • Cloudflare Tunnel

Projet réalisé dans le cadre du BTS SIO option SLAM (octobre 2026). L'organisation décrite ci-dessous est fictive.

Le besoin

L'Atelier Numérique du Pilat (organisation fictive) gère le parc informatique de six petites mairies et de leurs écoles. Les deux techniciens reçoivent toutes les demandes dans une seule boîte mail, sans tri : un simple « merci » arrive au même niveau qu'une panne qui bloque toute une mairie.

L'application classe et priorise automatiquement chaque message en JSON, pour que les techniciens traitent d'abord les urgences.

Ce que l'application ne fait pas

  • Elle ne répond pas à l'utilisateur : elle produit uniquement un JSON de tri.
  • Elle ne résout pas l'incident : elle ne fait que classer et prioriser.
  • Elle ne traite pas les pièces jointes ni les images.

Le modèle et la machine

Le modèle retenu est qwen3:8b, exécuté en local avec Ollama sur un Mac M4 avec 16 Go de mémoire unifiée. Il occupe environ 6 Go, ce qui laisse de la place pour macOS, Docker et les conteneurs. Il tourne à environ 6,5 tokens par seconde. Je l'ai comparé à qwen2.5:3b.

Les mesures

Un jeu de 12 cas, dont les 5 pièges du sujet (remerciement, hameçonnage, deux problèmes, changement de priorité, message vide), deux cas hors sujet et une tentative de détournement.

qwen3:8b (retenu)qwen2.5:3b (comparé)
Réussite (12 cas × 3 essais)100 % (36/36)67 % (24/36)
Temps de réponse médian9,3 s3,2 s

Le petit modèle est 3 fois plus rapide, mais il rate des priorités : il ne compte pas les personnes concernées par une panne et met tout en P3, et il passe à côté d'un cas d'hameçonnage. J'ai donc gardé qwen3:8b.

Les difficultés rencontrées

  • Temps de réponse trop long : Qwen3 générait une longue chaîne de réflexion avant de répondre. Ajouter /no_think dans le message utilisateur (et pas dans le prompt système, où il est ignoré) a fait passer le temps médian de 49 s à environ 9 s.
  • Conteneur Docker « unhealthy » : l'application pointait sur localhost, qui désigne le conteneur lui-même. Il faut utiliser host.docker.internal pour joindre Ollama sur la machine hôte.

La sécurité

  • URL publique : code d'accès et limite de 10 requêtes par minute et par visiteur.
  • Ollama non exposé : seul le conteneur applicatif lui parle, aucun port ouvert vers l'extérieur.
  • Détournement des consignes : consigne système stricte et un cas de test dédié.
  • Données personnelles : consigne « résumé sans nom de personne », vérifiée à la main sur les 12 cas.
  • Secrets : le fichier .env n'est jamais versionné, seul .env.example l'est.

Usage d'un assistant IA

J'ai utilisé un assistant IA (Claude) pour une première version du prompt, le débogage Docker et la structure du README. J'ai renforcé les règles du prompt après avoir observé des échecs, corrigé un test trop strict et refusé les suggestions qui simplifiaient trop les règles de priorité ou qui supprimaient des cas pour améliorer le score.

Mise en production

L'application est conteneurisée avec Docker Compose et exposée en HTTPS par un tunnel Cloudflare.
